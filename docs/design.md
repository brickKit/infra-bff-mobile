# infra/bff-mobile 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、查询与命令、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目 be-assembly-standard：
- 协议 20：入口（移动入口的会话与令牌）；
- 协议 17：外壳与资源；协议 09：审批的决定发给任务所属的组件；
- 决定 D68：基础组件不同步调用业务组件；本组件是它的例外之一（作为移动入口的组合层，被聚合的组件按客户装配明确列出、随入口发版）；
- AI 选择 A108：用 Go 实现，GraphQL 用 gqlgen，挂在 SDK 的用户面（Gin）上，可以进 Go 外壳。

首批范围是装配项目阶段计划 C11 的 P0 定的（AI 定，待复核）。

## 边界

移动入口的展示聚合：一次 GraphQL 查询供一个移动页面，数据从拥有它的组件取来、按页面的形状拼好；写操作只转发给属主。

| 不在这里 | 归谁 | 为什么 |
| --- | --- | --- |
| 任何业务规则（这张单能不能审批、这个价格对不对） | 属主组件 | 聚合层夹在前端与属主之间；规则放这里就等于放在前端 |
| 谁能看哪些行、哪些字段 | 属主组件的用户面（按调用者的授权与数据范围、字段控制） | 本组件不是数据的安全边界：它用调用者自己的凭据读，看到的就是调用者能看到的 |
| 数据库、缓存表、消息系统 | — | 没有自有数据；缓存要失效，失效要懂业务含义 |
| 编排多个写操作 | 属主组件 | 这里的写就是转发一次；再多就是要幂等、补偿的编排 |
| PC 入口的聚合 | 没有 | 底层选择“边缘”：聚合只给移动端，PC 直接调各组件 |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 根字段 | GraphQL 查询或变更的第一层字段，一个对应一个页面要的一块数据 | `Query.*`、`Mutation.*` |
| 持久化查询 | 移动入口构建时登记的查询文本，运行时只按它的摘要执行 | persisted query |
| 缺件 | 某个下游这次没装（字段不注册）或这次取不到（字段为空并带错误） | missing |
| 动作入口 | 待办条目里写的“决定发给哪个组件的哪个路径”，由统一待办按发布者推导 | `action` |

## 拥有的数据

没有：没有表、没有数据库角色、不连消息系统。唯一的状态在一次请求里：同一请求内取过的仓库目录（BM05），请求结束即丢。

## 规则

| 编号 | 规则 |
| --- | --- |
| BM01 | **入口**：用户面只有一条受保护的路由 `POST /api/bff-mobile/graphql`（操作 `infra.bff_mobile.entry.use`：使用移动入口，给移动端的用户；BrickKit 的健康与就绪照常）。请求体 `{"id": "<sha256>", "variables": {...}, "operationName": "..."}`：只按持久化查询的摘要执行（BM02）。答复是 GraphQL 的 JSON（`data`、`errors`），HTTP 状态 200；只有入口自己的拒绝（未认证、没有操作、请求体不对、查询不在清单）用 4xx 与问题详情 |
| BM02 | **持久化查询**：清单（摘要 → 查询文本）由移动入口的构建产出，部署配置 `BFF_PERSISTED_QUERIES` 给出（文件，`file://`）；启动时逐条按 schema 校验并计算深度与代价，任何一条不合 schema、超过上限，成员启动失败（不带着一份坏清单起来）。没有配置时清单为空，拒绝一切查询。摘要是查询文本的 SHA-256；不认识的摘要答 `PERSISTED_QUERY_NOT_FOUND`（400）。不支持运行时登记（APQ 的登记）：清单是有限的、能逐条测的一组 |
| BM03 | **上限**（第二道防线，清单之外漏进来的也挡住）：深度 6、代价 200（每个根字段 10、每个列表按它的 `limit` 计、其余字段 1）、别名 10、一次请求的执行时限 10 秒；列表的 `limit` 至多 50；按 id 取的批量至多 50 |
| BM04 | **读路径**：每个根字段经被聚合组件的**用户面**取，出站调用转发调用者的凭据（SDK 的 `ForwardUser`）；属主按调用者的授权、数据范围与字段控制答，本组件把答复按 schema 映射，没有的字段为空。**从不经系统面取用户看的数据**（系统面不按调用者过滤）。“我的”由属主判断：订单与商机的“我的”传 `owner_id` 为调用者本人（主体来自已核验的凭据，不来自变量） |
| BM05 | **一次请求内的复用**：同一请求里，可用量要的仓库目录只取一次（调用者看得到的全部仓库，至多 200 个），其余字段不缓存；跨请求不缓存任何东西。首批没有“按 id 批量补名称”的字段（订单、商机自带客户快照；产品页的产品是已知的），所以不引入批量加载器；以后有了按 id 补名称的字段，用属主的用户面批量读取，经每请求新建的批量加载器（未决问题） |
| BM06 | **时限与缺件**：每次下游调用的时限是请求剩余时间与 3 秒中较小的（SDK 的出站调用逐跳缩短）。一个根字段失败，只有它为空，`errors` 里带 `path`、`extensions.code`（属主答的原因，如 `NOT_FOUND`、`PERMISSION_DENIED`、`TASK_NOT_PENDING`；取不到时 `DEPENDENCY_UNAVAILABLE`、`DEADLINE_EXCEEDED`）与 `extensions.component`；同一页的其余字段照常返回。嵌套的非关键字段（产品的可用量）失败时，产品照常返回、可用量为空并带错误。前端据此区分“没有”与“暂时取不到” |
| BM07 | **按装配裁剪**：被聚合的组件都是可选依赖；没装的组件，它的根字段与嵌套字段在启动时不注册（schema 里就没有），持久化清单里用到它们的查询在启动时校验失败——清单与装配要一致，由移动入口的构建按客户基线产出。不留着字段永远返回空：introspection 会公布它，页面空白却不报错 |
| BM08 | **写路径：任务的决定**：变更 `decideTask(taskId, version, decision, comment, idempotencyKey)`。本组件先以调用者的凭据从统一待办读这个任务的条目（`GET /api/workflow/tasks/{id}`），**动作入口取自条目**（统一待办按发布者推导），不取自客户端；入口的组件必须是本组件的依赖并且这次装了，路径必须是 `/be/flow/tasks/{id}/decisions` 的形状且 `{id}` 等于这个任务，否则答 `REQUEST_INVALID`；然后把决定转发过去（转发调用者的凭据与 `Idempotency-Key`）。属主的答复原样映射（`VERSION_CONFLICT`、`SELF_APPROVAL`、`TASK_NOT_PENDING` 等）。本组件不重试写（幂等键由客户端给，重试由客户端决定） |
| BM09 | **写路径：通知已读**：`markNotificationRead(id)`、`markAllNotificationsRead`，转发给通知组件（凭据与幂等键照转） |
| BM10 | **错误不泄露细节**：属主答的问题详情只取 `reason` 映射成 `extensions.code`，`detail` 不转给客户端（属主的 `detail` 写给开发者，可能带内部的名字）；本组件自己的失败只写日志，客户端看到通用的 `INTERNAL` 与追踪编号 |
| BM11 | **合并安全**：本组件只经 SDK 的运行时与出站调用；gqlgen 的执行器在组件里创建，不注册任何进程级的东西；一个成员一个执行器 |
| BM12 | **观测**：每个根字段一个指标（次数、耗时、按 `code` 分的失败），每次下游调用由 SDK 的出站调用计数；日志不记变量（可能带搜索词等个人数据），只记查询的摘要与根字段 |

## 查询与命令

| 根字段 | 下游（用户面，转发调用者凭据） | 说明 |
| --- | --- | --- |
| `myTasks(taskType, cursor, limit)` | `infra/workflow` `GET /api/workflow/tasks` | 我的待办；条目带任务投影的摘要（标题与至多 20 个字段）、动作入口、是否失联 |
| `task(id)` | `infra/workflow` `GET /api/workflow/tasks/{id}` | 任务详情：摘要即单据的要点，首批不再去属主取整张单据（未决问题） |
| `myNotifications(unread, cursor, limit)` | `infra/notification` `GET /api/notification/messages` | 带未读数 |
| `products(q, cursor, limit)`、`product(id)` | `mdm/product` `GET /api/product/products`、`/{id}` | 产品的可用量是嵌套字段 `availability`：`erp/inventory` `GET /api/inventory/positions?product_id=`，仓库名称来自同一请求取一次的 `GET /api/inventory/warehouses`（BM05） |
| `customers(q, cursor, limit)`、`customer(id)` | `mdm/partner` `GET /api/partner/partners`、`/{id}` | |
| `myOrders(state, cursor, limit)`、`order(id)` | `erp/sales` `GET /api/sales/orders?owner_id=<我>`、`/{id}` | 订单自带客户快照 |
| `myOpportunities(stage, cursor, limit)`、`opportunity(id)` | `crm/opportunity` `GET /api/opportunity/opportunities?owner_id=<我>`、`/{id}` | |
| `decideTask(...)` | 条目里的动作入口（`erp/purchase`、`erp/payment` 等） | BM08 |
| `markNotificationRead(id)`、`markAllNotificationsRead` | `infra/notification` | BM09 |

列表都按属主的游标分页（`cursor`、`limit`，答 `nextCursor`），不用偏移量。

## 部署与替换

- **放置**：无状态、低负载；放外壳 `be/go-core`（与它聚合的业务成员同壳，调用仍走网络）或单跑。端口 8500（注册表），不暴露系统面。
- **边缘**：`/api/bff-mobile/` 经边缘的移动会话（协议 20）；边缘的路由超时要大于 BM03 的执行时限，否则边缘先答 504、本组件还在调下游。
- **替换**：同 schema 的实现或 Fork；移动入口与它一起发版。

## 取舍

- **GraphQL**：kb知识库的建议是三种以上的自家客户端对同一批数据要不同形状时才用 GraphQL（固定成本：按类型授权、批量加载、白名单、按代价限流）。本项目只有移动入口一个客户端，用它是 A108 的决定（维护者 2026-10-16 确认）：移动页面的形状常变、网络差，一次请求取齐一页比按页面加接口合适。固定成本这样付：授权在属主（本组件转发调用者凭据，BM04）；白名单与上限（BM02、BM03）；批量加载首批用不上（BM05）；按代价限流在边缘或以后（未决问题）。
- **只走用户面**：系统面更快（不过授权），但不按调用者过滤；为聚合省下的时间不值得冒“替用户取了他看不到的数据”的风险。

## 验证故事

- 一个下游超时，其余部分照常返回，超时的那部分为空并标明 `DEADLINE_EXCEEDED` 与组件（边界卡）。
- 移动端用户在待办里同意一张采购申请：决定经本组件转发给 `erp/purchase`，任务离开待办；同一个幂等键再发，答一样的结果。
- 客户端伪造动作入口（指向别的组件或路径）：被拒，什么也不转发。
- 没装 `crm/opportunity` 的部署：schema 里没有商机的字段，用到它的持久化查询让启动失败。

## 未决问题

- **单据详情**：首批的任务详情只有投影的摘要；要看整张单据时，按任务类型去属主取（要一张“任务类型 → 单据的用户面路径”的表，或流程内核在投影里给出单据的读取入口）。
- **按 id 补名称**：以后有列表要补别的组件的名称时，属主要有用户面的批量读取（例如 `GET /api/product/products?ids=`），本组件经每请求新建的批量加载器取。
- **按代价限流**：每个调用者单位时间的代价额度，放边缘还是本组件。
- **2.x 的权限键**：注册表里有旧版的 `infra.bff-mobile.*` 键；新设计只用一个入口操作 `infra.bff_mobile.entry.use`，旧键不复用、不改名（注册表只追加）。
