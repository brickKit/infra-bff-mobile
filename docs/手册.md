# infra-bff-mobile · 使用手册

## 1. 项目结构

```
infra-bff-mobile/
├── component.yaml
├── assembly.yaml                     # default 角色；无 data 段（零数据库）；data_scopes: none；无 shell 段（不进外壳）
├── buf.yaml                          # 只 lint contracts/vendor（依赖方契约镜像），不生成代码
├── contracts/
│   ├── schema.graphql                # 唯一真相源，手写 SDL，按前端页面裁剪（设计计划 §3.1）
│   ├── persisted-operations.json     # 构建期产物，哈希→查询文本，当前是空清单
│   └── vendor/mdm/{customer,product}/v1/*.proto   # 只 vendor 这两个——其余三个走 REST 不需要 gRPC codegen
├── src/
│   ├── main.ts                       # besdk.runStandalone(createModule)
│   ├── module.ts                     # 唯一入口 createModule(rt)
│   ├── schema.ts                     # 解析 contracts/schema.graphql，按装配裁剪 Query 字段
│   ├── dependencies.ts               # 字段 → 弱依赖 的登记表 + 装配可用性判断
│   ├── context.ts                    # 每请求 GraphQL context，DataLoader 现造
│   ├── persistedOperations.ts        # 读 contracts/persisted-operations.json
│   ├── clients/
│   │   ├── grpcProto.ts              # @grpc/proto-loader 动态加载 + Promise 化调用
│   │   ├── customer.ts / product.ts  # gRPC BatchGet 客户端 + DTO 映射
│   │   └── restForward.ts            # REST 转发（原样带 Authorization）
│   └── resolvers/                    # 唯一放 resolver 的目录，make gates 的裸 resolver 扫描认这里
├── scripts/checkSchema.ts            # make contract-check 用
├── test/
├── Dockerfile / Makefile
```

## 2. 功能详解

- **两类读走两条路径，判据是"这个组件的 assembly.yaml 有没有真 data_scopes"**（`contracts/schema.graphql` 顶部注释、`AGENTS.md`）：`mdm-customer`/`mdm-product` 是 `data_scopes: none`，走 `src/clients/customer.ts`/`product.ts` 的 gRPC `BatchGet` + `besdk.createBatchGetLoader`；`erp-sales`（org/owner）、`erp-inventory`（warehouse，mode: in）、`infra-workflow`（org/owner）都有真实数据权限，改走 `src/clients/restForward.ts` 原样转发 `Authorization` 头去打各自的 REST 端点——这是阶段三 Task 11 实现时发现的一个真实数据权限缺口，用户明确拍板的方向。
- **`schema.ts` 的裁剪只动 Query 的字段，不清理没人引用的类型定义**：`buildSchema()` 解析 `contracts/schema.graphql` 一次，按 `dependencies.ts` 的 `FIELD_TO_DEPENDENCY` 表过滤掉未装配组件对应的 Query 字段，再喂给 `makeExecutableSchema`。⚠️ `resolverValidationOptions: { requireResolversToMatchSchema: "ignore" }` 是必须的——`resolvers/index.ts` 的汇总表永远是全量的（五个组件的全部 resolver 都在），schema 按装配裁剪过，"resolver 比 schema 多"是设计本身的常态，`@graphql-tools/schema` 默认会把这种情况当错误抛出。
- **`inventoryBalance` 没有 DataLoader 批量版本**：`erp-inventory` 的 `GET /balances` 只有单条查询端点，没有批量端点；`inventoryBalance(productId, warehouseId)` 与 `order(id)` 一样是"给定已知 id 查一条"，不强求防 N+1。
- **`myTasks`/`order`/`inventoryBalance` 用的是裸 `fetch()`，不是 `besdk.userClient`/`systemClient`**：那两个是 gRPC 专用，REST 转发是全新的需求（`restForward.ts`），`besdk.endpoint()` 剥掉了 scheme（gRPC 客户端要裸 `host:port`），REST 调用要重新拼上 `http://`。
- **Persisted Operations 的哈希用的是标准 Apollo APQ 格式**（`extensions.persistedQuery.{version:1, sha256Hash}`），`getPersistedOperation` 只是一次 `manifest[hash]` 查表，不做"首次上报自动注册"这种运行时写入——清单是构建期产物，运行时只读。

## 3. 完整契约清单

**对外：GraphQL over HTTP，单一端点 `POST /graphql`。** 完整字段清单见 [`contracts/schema.graphql`](../contracts/schema.graphql)（本身就是权威契约文本，不重复抄一遍）。

**权限键**（`assembly.yaml` 的 `permissions` 段，每个字段一个）：

| 权限键 | 对应字段 |
|---|---|
| `infra.bff-mobile.customer.view` | `customer` / `customers` |
| `infra.bff-mobile.product.view` | `product` / `products` |
| `infra.bff-mobile.order.view` | `order` / `myOrders` |
| `infra.bff-mobile.inventory.view` | `inventoryBalance` |
| `infra.bff-mobile.task.view` | `myTasks` |

**gRPC：无。** 只作为客户端调 `mdm-customer`/`mdm-product`，不对外提供 gRPC。

**事件：无。** 发布/消费都没有——不持有任何状态。

详细判据见 `docs/design/infra-bff-mobile.md`。

## 4. 数据模型

**无。零持久化数据，没有 schema/role（§6.5 铁律二）。**

唯一的"状态"是进程内的两样东西，都随重启清空：DataLoader 的批次缓存（单次请求内）、authz bundle 的内存 map（`besdk` 管，15 秒轮询刷新）。

**实测验证**（真实 mdm-customer/mdm-product/infra-workflow 容器，非 mock）：schema 按装配裁剪（没装的组件字段根本不在 schema 里）、gRPC `BatchGet` 真实往返（枚举前缀剥离、缺失 id 按顺序补 `undefined`）、真实子进程起服务后 401/403/200 三态、REST 转发真实把 `Authorization` 头送到了 `infra-workflow`（用真实容器的真实拒绝响应证明，不是假设）、Docker 镜像内在 Node 20 上真实跑通 gRPC 查询全链路。

## 5. 开发

```bash
npm install
npm run typecheck
npm test
```

多数测试需要真实容器，缺省时自动跳过（`describe.skipIf`）：

```bash
# gRPC 客户端测试——需要真实 mdm-customer/mdm-product
MDM_CUSTOMER_ENDPOINT=http://<IP>:9090 MDM_PRODUCT_ENDPOINT=http://<IP>:9092 \
  TEST_CUSTOMER_ID=<真实id> TEST_PRODUCT_ID=<真实id> npm test -- test/clients.test.ts

# 端到端——另需真实 infra-workflow
TEST_MDM_CUSTOMER_ENDPOINT=http://<IP>:9090 TEST_INFRA_WORKFLOW_ENDPOINT=http://<IP>:8201 \
  TEST_CUSTOMER_ID=<真实id> npm test -- test/e2e.test.ts
```

⚠️ `test/e2e.test.ts` 会真的监听 `component.yaml` 里写死的端口 8500——本机不能有别的进程占着这个端口（包括没清理干净的上一次手动调试进程）。测试会临时改写 `contracts/persisted-operations.json` 再在 `finally` 里还原，不会污染仓库状态。

`test/clients.test.ts`/`test/e2e.test.ts` 用的测试客户/产品要提前用 `grpcurl` 真实 `Create` 出来（不是种子数据）——因为这两张表没有为测试预留的固定记录，`id` 每次真实分配，用完记得清理（`DELETE FROM mdm_customer.customers WHERE id = ...`）。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `/graphql` 对任何查询都返回 `PersistedQueryOnly`，HTTP 状态码还是 200 | `persisted_queries_only: true` 挡在最前面，客户端发的是裸 `query` 字符串，不是 `extensions.persistedQuery.sha256Hash` | 改用 Apollo APQ 格式发请求；确认 `contracts/persisted-operations.json` 里有这个哈希对应的条目 |
| `npm install` 之后 `import { ... } from "besdk"` 报 `Cannot find module` | `be-sdk-ts@<0.3.1` 没有 `prepare` 脚本，`npm install` 装 git 依赖时不会编译 `dist/`；`<0.3.2` 补了 `prepare` 但 `dist/` 还是被 `.gitignore` 兜底过滤掉打包不进去 | 确认依赖的是 `be-sdk-ts@>=0.3.2`（`package.json` 里 `besdk` 那一行的 tag） |
| gRPC 调 `mdm-customer` 直接抛 `Cannot compose insecure credentials` | `be-sdk-ts@<0.3.3` 的 `userClient` 试图把 CallCredentials 组合进 insecure ChannelCredentials，`@grpc/grpc-js` 故意拒绝这个组合 | 确认依赖 `be-sdk-ts@>=0.3.3` |
| `npm test`/`npm run typecheck` 报 `Cannot use ... from another module or realm` | 依赖树里存在两份 `graphql` 包（`@escape.tech/graphql-armor*` 系列容易触发），graphql-js 的 `instanceof` 检查跨包失败 | `package.json` 的 `overrides.graphql` 已经钉死版本，改动依赖后重新 `rm -rf node_modules package-lock.json && npm install` 确认只有一份 `node_modules/graphql` |
| `myTasks`/`order` 返回的 GraphQL 错误永远是 "Unexpected error." | Yoga 默认掩盖未捕获异常（含 REST 转发失败）——这是刻意的安全默认，不是 bug | 看子进程/容器日志里 `restForward.ts` 打的真实错误消息（状态码/URL），不要试图去改 Yoga 的掩盖行为 |
